# Security boundaries

Each item of the plan's security acceptance checklist, mapped to the code that
enforces it, the tests that prove it, and where that proof runs. The
mechanisms are explained in [security-model.md](security-model.md); assets,
trust boundaries and residual risks are in [threat-model.md](threat-model.md).
Whether each CI job has actually run and passed is tracked in
[verification.md](verification.md); this page says only where a proof is
meant to run. Recorded on 2026-10-17.

"CI" means [ci.yml](../.github/workflows/ci.yml) on `ubuntu-latest` and
`windows-latest` unless a platform is named. "CI (Windows)" means a test that
only runs on `windows-latest`, with the Microsoft Software Key Storage Provider
because hosted runners have no TPM. "Fuzz" means
[fuzz.yml](../.github/workflows/fuzz.yml); "MSI" means the `msi` jobs that run
[msi-lifecycle.ps1](../.github/scripts/msi-lifecycle.ps1). "Manual" means a
documented procedure that has not been executed, or a gap with no procedure.

## Accepted limitations

These are limits of the design, not open defects:

- Other local programs running with the same OS privileges as the user can
  use the local proxy. See
  [security-model.md](security-model.md#what-it-does-not-protect).
- Session credentials keep out local programs that do not know them, not
  programs running as the same user, which can ask the agent for them; and
  nothing technical stops a user from typing them into a website dialog that
  imitates the proxy sign-in. See
  [security-model.md](security-model.md#local-proxy-authentication-session_credentials).
- Gateinto does not force system-wide traffic through the proxy; only clients
  configured to use it are proxied. See
  [threat-model.md](threat-model.md#non-goals).
- Gateinto does not authorize access to services on the remote Edge's behalf;
  authorization stays with the upstream. See
  [threat-model.md](threat-model.md#non-goals).

## Routing selection

Gateway routing is the default. A URI can choose mixed routing for only its
new browser session; no extra prompt is required for a known gateway. This
is not an enforced gateway policy. Direct connections expose source IP and
local DNS and bypass gateway authorization; IP matching is a heuristic.
See [session routing](protocol/launch-uri.md#session-routing).

`src/proxy/routing.rs` bounds DNS and direct TCP within half the opening
deadline, uses resolved addresses without another target lookup, and skips
local DNS entirely in gateway mode. Its unit tests inject DNS errors, empty
answers, overlapping/mapped addresses and a stalled resolver. Loopback
`tests/mixed_routing.rs` covers direct relay, inner TLS, early data,
half-close, fallback statuses, authentication, no replay and shutdown.
`tests/launch.rs` covers the URI-to-binary-to-agent pipeline and concurrent
session isolation; `tests/agent.rs` covers retention through approval without
saving the mode; `tests/h2_connect.rs` covers mixed gateway routes sharing
HTTP/2. These tests run in CI; real browser routing remains Manual in
[browser-verification.md](browser-verification.md#mixed-routing-launch-links).
